# 02. 개발 계획 · 로드맵

## 원칙

1. **항상 플레이 가능한 상태 유지.** 매 마일스톤 끝에 `main` 이 Pages 에 배포되고 처음부터 끝까지(현재 구현 범위) 플레이된다.
2. **스토리 먼저, 그림 나중.** 전 챕터를 플레이스홀더 그래픽으로 완주한 뒤 에셋을 교체한다. 소설이 이미 완성돼 있으므로 텍스트 파이프라인이 가장 빠른 길이다.
3. **코드보다 데이터.** 챕터는 JSON. 새 챕터 = 새 JSON 파일 + 레지스트리 등록. 엔진 코드를 건드리는 건 새 연출 명령이 필요할 때뿐.
4. **커밋 단위 = 챕터 or 시스템 하나.** `validate:script` 와 `typecheck` 가 통과해야 push.

## 순서를 이렇게 잡은 이유

- M1 을 M2 앞에 두는 이유: 회상 챕터(4~8장)는 화면 효과·표정 교체·BGM 없이는 쓰기 어렵다. 명령이 없으면 JSON 을 나중에 다시 고쳐야 한다.
- 에셋을 마지막에 두는 이유: AI 생성 에셋은 "어떤 컷이 실제로 필요한지" 플레이해 보고 결정하는 게 낭비가 적다. 특히 CG 는 플레이스홀더 상태에서 씬 타이밍을 먼저 잡는다.

## 작업 방식 (Claude Code 와 함께)

- 새 챕터: "ch04 를 소설 §4 「예언」에서 변환해 줘" → JSON 작성 → `npm run validate:script` → 브라우저에서 확인 → 커밋.
- 새 명령: `types.ts` 에 타입 추가 → `ScriptRunner.exec` 에 케이스 → `StageHooks` 에 훅 → `ChapterScene` 구현 → `validate-chapters.mjs` 허용 목록 추가.
- 에셋 교체: 파일을 `public/assets/<종류>/` 에 넣고 `manifest.json` 배열에 키 추가. 코드 수정 없음.

## 브랜치 · 배포

- `main` = 항상 배포 가능. push 시 GitHub Pages 자동 배포.
- 챕터·기능은 `feat/ch04`, `feat/bgm` 같은 브랜치에서 작업 후 머지 (혼자 개발이면 `main` 직접 커밋도 허용, 단 validate/typecheck 통과 필수).
- 태그: `v0.1` (M0), `v0.5` (M3), `v0.9` (M4), `v1.0` (M5).
